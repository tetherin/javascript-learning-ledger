## Session plan and teaching record

1. **Own, inherited, enumerable, and non-enumerable properties.** Revisit the Q1 misconception. `Object.keys()`, `Object.values()`, and `Object.entries()` operate on own enumerable string-keyed properties. Integer-index-like keys are ordered numerically first; other string keys retain insertion order. Example:
   ```js
   const proto = { inherited: true };
   const record = Object.create(proto);
   record.region = "IN";
   Object.defineProperty(record, "secret", { value: 7 });
   record["10"] = "ten";
   record["2"] = "two";
   console.log(Object.keys(record)); // ["2", "10", "region"]
   console.log(Object.values(record)); // ["two", "ten", "IN"]
   console.log(Object.entries(record)); // [["2", "two"], ["10", "ten"], ["region", "IN"]]
   ```

2. **`Object.hasOwn()` versus `in` and enumerability.** `in` checks the object and its prototype chain. `Object.hasOwn()` checks direct ownership even for non-enumerable properties. `propertyIsEnumerable()` additionally requires an own property to be enumerable. Use `Object.hasOwn()` for robust own-property checks instead of calling a potentially shadowed `obj.hasOwnProperty()`.

3. **Inspecting property descriptors.** `Object.getOwnPropertyDescriptor(obj, key)` returns the descriptor for an own property, or `undefined` if that own property does not exist. Data descriptors expose `value` and `writable`; accessor descriptors expose `get` and `set`. Both have `enumerable` and `configurable`.

4. **Defining properties precisely.** `Object.defineProperty()` returns the original object. When creating a property, omitted `writable`, `enumerable`, and `configurable` flags default to `false`; ordinary assignment creates a normal own enumerable, writable, configurable data property. Do not assume a defined property will appear in `Object.keys()`.

5. **`Object.seal()` versus `Object.freeze()`.** Both mutate and return the same object; neither creates a copy. Sealing prevents adding/removing/reconfiguring properties but existing writable data values can still change. Freezing also makes existing data properties non-writable. Both are shallow: nested objects are not recursively sealed/frozen.

6. **`map()` versus `forEach()` in real code.** `map()` returns a new array of callback results; `forEach()` returns `undefined` and is intended for side effects. An async `forEach` callback is not awaited. Use `Promise.all(items.map(async ...))` for concurrent work, or `for...of` with `await` for sequential work.

7. **`sort()` versus `toSorted()` and comparator correctness.** `sort()` mutates and returns the original array; `toSorted()` returns a new shallow-sorted array. The default comparison is string-based, so numeric data needs a comparator such as `(a, b) => a - b`. A comparator must be consistent; inconsistent comparison logic can produce engine-dependent results.

8. **Prototype chains and safe dictionaries.** Ordinary objects inherit from `Object.prototype`; therefore `"toString" in {}` is true even though it is not an own data key. For dynamic key-value dictionaries, consider `Map` or `Object.create(null)`. Validate keys and avoid blindly merging untrusted `__proto__`, `constructor`, or `prototype` keys into objects; this is a prototype-pollution risk.

9. **Normalize query objects without mutating the input.** `Object.entries()` → `filter()` → `map()` → `Object.fromEntries()` is a useful transformation pipeline. It creates a new object, but filtering allowed keys does not prove required keys exist or that their values are valid.

   ```js
   const allowed = new Set(["page", "limit", "sort"]);
   const normalized = Object.fromEntries(
     Object.entries(rawQuery)
       .filter(([key]) => allowed.has(key))
       .map(([key, value]) => [
         key,
         key === "page" || key === "limit" ? Number(value) : value
       ])
   );
   ```

10. **Validate shape, presence, syntax, range, and allowlisted values separately.** First reject null, arrays, and non-object inputs. Then decide whether unknown keys should be rejected or stripped. Require own fields with `Object.hasOwn()`; parse numeric strings according to the API's accepted syntax; use `Number.isSafeInteger()` plus explicit positive/range checks; and validate `sort` against an allowlist. For production Express inputs, remember that query-parser output may be more complex than a flat string record; a schema validator such as Zod can enforce the contract at the boundary.

### Exercise B: bug-finding and case-based reasoning
A Node/Express route receives query parameters for pagination. Review this check:

```js
function getLimit(query) {
  if ("limit" in query) {
    return Number(query.limit);
  }
  return 20;
}
```

Identify at least two correctness/security problems. Explain what should be checked before trusting `limit`. Then implement a `validateQuery(query)` that:
- accepts a plain object with own `page`, `limit`, and `sort` fields;
- accepts positive decimal-integer strings for `page` and `limit`;
- requires `page >= 1` and `1 <= limit <= 100`;
- allows only `createdAt` or `updatedAt` for `sort`;
- rejects unknown keys (this is the chosen contract for this exercise);
- does not mutate the original input.

Do not submit a memorized code dump: explain why each validation stage is in that order. Treat the exact allowed sort fields and limit as exercise-specific API rules, not universal defaults.
