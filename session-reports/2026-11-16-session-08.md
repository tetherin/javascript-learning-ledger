## Exactly 10 concepts taught

### 1. Think of every property using three independent dimensions

A property can be:
- own or inherited;
- enumerable or non-enumerable;
- string-keyed or Symbol-keyed.

These are independent dimensions. "Own" does not mean "enumerable", and "accessible" does not mean "enumerated".

~~~js
const parent = {};
Object.defineProperty(parent, "inheritedHidden", {
  value: 1,
  enumerable: false
});
Object.defineProperty(parent, "inheritedVisible", {
  value: 2,
  enumerable: true
});

const record = Object.create(parent);
record.visible = 3;

Object.defineProperty(record, "hidden", {
  value: 4,
  enumerable: false
});

const metadata = Symbol("metadata");
record[metadata] = 5;

console.log(record.inheritedVisible); // 2
console.log(Object.hasOwn(record, "hidden")); // true
console.log(Object.keys(record)); // ["visible"]
~~~

Mental model: property access follows the prototype chain; own-property inspection and enumeration APIs apply their own filters. Do not infer one from the other.

Reference: https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Enumerability_and_ownership_of_properties

### 2. Choose the correct own-key inspection API

~~~js
console.log(Object.keys(record));
// ["visible"]

console.log(Object.getOwnPropertyNames(record));
// ["visible", "hidden"]

console.log(Object.getOwnPropertySymbols(record));
// [Symbol(metadata)]

console.log(Reflect.ownKeys(record));
// ["visible", "hidden", Symbol(metadata)]
~~~

- \`Object.keys\`: own, enumerable, string keys.
- \`Object.getOwnPropertyNames\`: all own string keys, including non-enumerable.
- \`Object.getOwnPropertySymbols\`: all own Symbol keys, including non-enumerable.
- \`Reflect.ownKeys\`: all own string and Symbol keys, regardless of enumerability.

For ordinary objects, integer-index-like string keys are ordered first numerically, then other string keys in creation order, then Symbols in creation order. \`Reflect.ownKeys\` is useful for complete introspection, not ordinary DTO serialization.

References:
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Reflect/ownKeys
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/getOwnPropertyNames

### 3. A \`for...in\` loop walks enumerable string keys on the prototype chain

~~~js
const base = { inherited: true };
const item = Object.create(base);
item.own = true;

for (const key in item) {
  console.log(key);
}
~~~

Output:

~~~text
own
inherited
~~~

If the task is specifically to process an object's own enumerable string properties, guard the loop:

~~~js
for (const key in item) {
  if (!Object.hasOwn(item, key)) continue;
  console.log(key, item[key]);
}
~~~

For most own-key transformations, \`Object.keys()\` plus \`for...of\` is simpler. Remember that \`for...in\` does not enumerate Symbol keys.

Reference: https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Enumerability_and_ownership_of_properties

### 4. Separate ownership from enumerability

| Property kind | \`Object.hasOwn\` | \`in\` | \`propertyIsEnumerable\` |
|---|---:|---:|---:|
| Own enumerable | true | true | true |
| Own non-enumerable | true | true | false |
| Inherited enumerable | false | true | false |
| Inherited non-enumerable | false | true | false |

~~~js
const prototype = { inherited: 1 };
const value = Object.create(prototype);

Object.defineProperty(value, "hidden", {
  value: 2,
  enumerable: false
});

console.log(Object.hasOwn(value, "hidden")); // true
console.log("hidden" in value); // true
console.log(value.propertyIsEnumerable("hidden")); // false

console.log(Object.hasOwn(value, "inherited")); // false
console.log("inherited" in value); // true
~~~

Use \`Object.hasOwn(value, key)\` for own-property presence. It remains reliable when an object has no \`hasOwnProperty\` method or shadows that method. Use \`in\` only when inherited properties should count.

Reference: https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Enumerability_and_ownership_of_properties

### 5. \`Object.defineProperty()\` defaults are restrictive and it does not invoke a setter

~~~js
const prototype = {
  set mode(value) {
    console.log("setter called", value);
  }
};

const settings = Object.create(prototype);

const returned = Object.defineProperty(settings, "mode", {
  value: "safe"
});

console.log(returned === settings); // true
console.log(Object.keys(settings)); // []
console.log(Object.getOwnPropertyDescriptor(settings, "mode"));
~~~

The descriptor is equivalent to:

~~~js
{
  value: "safe",
  writable: false,
  enumerable: false,
  configurable: false
}
~~~

No inherited setter message is printed. \`Object.defineProperty\` uses property-definition semantics rather than ordinary assignment's setter path. The method returns the original object.

Production tip: specify \`writable\`, \`enumerable\`, and \`configurable\` explicitly when the intended behavior matters. Do not rely on restrictive defaults accidentally.

Reference: https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/defineProperty

### 6. Non-configurable does not always mean the value can never change

A non-configurable data property that is still writable has a narrow legal transition:

~~~js
const state = {};

Object.defineProperty(state, "status", {
  value: "pending",
  writable: true,
  enumerable: true,
  configurable: false
});

Object.defineProperty(state, "status", {
  value: "complete"
}); // allowed; omitted flags retain their current values

Object.defineProperty(state, "status", {
  writable: false
}); // allowed: writable true -> false

// A later attempt to make writable true again throws TypeError.
~~~

Once a non-configurable data property becomes non-writable, its value cannot be changed to a different value. Its descriptor cannot be converted to an accessor, deleted, or made configurable again.

This matters when designing property-based invariants and when interpreting a failed redefinition: inspect the current descriptor, not just the property value.

Reference: https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/defineProperty

### 7. \`preventExtensions\`, \`seal\`, and \`freeze\` protect different things

| Operation | Add properties | Delete/reconfigure existing properties | Change existing writable data values |
|---|---|---|---|
| \`preventExtensions\` | No | Yes, if configurable | Yes, if writable |
| \`seal\` | No | No | Yes, if writable |
| \`freeze\` | No | No | No |

All three modify and return the same object. They are shallow:

~~~js
const settings = Object.freeze({
  nested: { enabled: true }
});

settings.nested.enabled = false;

console.log(settings.nested.enabled); // false
console.log(Object.isFrozen(settings)); // true
console.log(Object.isFrozen(settings.nested)); // false
~~~

Freezing a configuration's outer object does not recursively freeze nested configuration. If deep immutability is required, define and test a deliberate deep-freeze policy or use immutable data structures. Do not assume \`Object.freeze\` performs a deep clone.

References:
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/preventExtensions
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/seal
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/freeze

### 8. Dynamic object keys can create prototype-related hazards

Consider an untrusted JSON payload:

~~~js
const payload = JSON.parse(
  '{"__proto__":{"isAdmin":true}}'
);

const merged = Object.assign({}, payload);

console.log(Object.getPrototypeOf(merged) === Object.prototype); // false
console.log(merged.isAdmin); // true (inherited from the new prototype)
~~~

This example changes the prototype of the newly created \`merged\` object; it does not by itself modify the global \`Object.prototype\`. Recursive merge utilities and unsafe dynamic assignment can create more severe prototype-pollution vulnerabilities.

Safer choices:
- validate and allowlist accepted keys;
- use \`Map\` for arbitrary dynamic keys;
- use \`Object.create(null)\` for a dictionary that must be an object;
- avoid blindly merging untrusted keys into ordinary objects.

A null-prototype object has no inherited \`Object.prototype\` setters or methods, so account for that when using it with APIs that expect ordinary objects.

Reference: https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/Prototype_pollution

### 9. A Zod schema can be the runtime boundary for Express query data

TypeScript types do not validate a request at runtime. Express documents that \`req.query\` is user-controlled and its shape depends on the configured query parser.

This example uses Zod 4's \`z.strictObject\` API:

~~~ts
import { z } from "zod";

const pageSchema = z.string()
  .regex(/^[1-9]\\d*$/)
  .transform(Number)
  .pipe(
    z.number()
      .int()
      .min(1)
      .refine(Number.isSafeInteger)
  );

const limitSchema = z.string()
  .regex(/^[1-9]\\d*$/)
  .transform(Number)
  .pipe(
    z.number()
      .int()
      .min(1)
      .max(100)
      .refine(Number.isSafeInteger)
  );

const listQuerySchema = z.strictObject({
  page: pageSchema,
  limit: limitSchema.default(20),
  sort: z.enum(["createdAt", "updatedAt"]).default("createdAt")
});

const result = listQuerySchema.safeParse(req.query);

if (!result.success) {
  return res.status(400).json({ error: "Invalid query" });
}

const query = result.data;
// query is validated and transformed; req.query was not mutated.
~~~

Important distinctions:
- \`parse()\` returns parsed data or throws a ZodError.
- \`safeParse()\` returns a discriminated success/error result.
- \`z.object()\` strips unknown keys by default in current Zod; \`z.strictObject()\` rejects them.
- The regex checks the original string format before conversion, so values such as whitespace, decimals, zero, and leading-zero forms are rejected by this policy.
- This snippet uses Zod 4. In Zod 3, strict object schemas are commonly written as \`z.object({...}).strict()\`.

References:
- https://zod.dev/basics
- https://zod.dev/api?id=objects
- https://expressjs.com/en/5x/api/request/

### 10. \`Object.fromEntries()\` creates data properties; duplicate keys use the last value

~~~js
const result = Object.fromEntries([
  ["role", "reader"],
  ["role", "admin"],
  ["__proto__", { isAdmin: true }]
]);

console.log(result.role); // "admin"
console.log(Object.hasOwn(result, "__proto__")); // true
console.log(Object.getPrototypeOf(result) === Object.prototype); // true
console.log(result.isAdmin); // undefined
~~~

The later \`role\` entry replaces the earlier value. The \`"__proto__"\` entry is created as an own data property here; it does not set the new object's prototype.

But this object can become dangerous if it is later copied with an operation that invokes a target setter, such as \`Object.assign({}, result)\`. The safety of one construction operation does not make the whole data pipeline safe.

Use an allowlist before converting untrusted entries, and inspect how downstream merge operations behave.

References:
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/fromEntries
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Object_initializer
