## Exactly 10 concepts taught

### 1. Object.assign versus spread: target setters and identity
- Object.assign mutates and returns its target; it reads source values and writes using target Set semantics, so inherited setters can run.
- Object spread creates a new object and defines copied properties on it; it does not invoke an inherited setter on the source object's prototype as a target setter.
- Both are shallow, and both can evaluate enumerable source getters.

### 2. Source getters versus descriptor copying
- Object.assign and object spread evaluate enumerable own source getters to obtain values.
- The copied result contains an ordinary data property, not the source accessor descriptor.
- Object.getOwnPropertyDescriptors retrieves the getter function without invoking it.
- Creating a copy with Object.create(Object.getPrototypeOf(source), Object.getOwnPropertyDescriptors(source)) retains the accessor and prototype, but remains shallow.

### 3. Object.assign can partially mutate before throwing
- Object.assign processes source properties sequentially.
- If a later write fails, it throws but does not roll back earlier successful writes.
- Do not treat Object.assign as an atomic or transactional merge.

### 4. Nested object spread is shallow replacement, not recursive merge
- Later top-level properties overwrite earlier properties.
- If overrides.headers exists, a shallow merge replaces the complete headers object.
- Merge nested headers explicitly when the intended policy is to preserve default headers and override selected keys.
- Validate merge inputs; shallow spread is not a general-purpose safe deep-merge utility.

### 5. Safe parseLimit(query: unknown) boundary
The example policy accepts only positive decimal integer strings from 1 through 100, defaults to 20 only when the own property is absent, rejects present-but-undefined, and does not mutate input.

~~~ts
function parseLimit(query: unknown): number {
  if (
    query === null ||
    typeof query !== "object" ||
    Array.isArray(query)
  ) {
    throw new Error("Invalid query");
  }

  if (!Object.hasOwn(query, "limit")) {
    return 20;
  }

  const value = (query as Record<string, unknown>).limit;

  if (
    typeof value !== "string" ||
    !/^[1-9]\d*$/.test(value)
  ) {
    throw new Error("Invalid limit");
  }

  const limit = Number(value);

  if (!Number.isSafeInteger(limit) || limit > 100) {
    throw new Error("Invalid limit");
  }

  return limit;
}
~~~

### 6. Bounded worker pool for partial outcomes
- Promise.allSettled collects fulfillment/rejection outcomes but does not cap how many operations start.
- A fixed number of workers can pull the next index, await one task, store its outcome at that index, and continue.
- Storing by original index preserves input order even when tasks finish out of order.
- A worker pool maintains up to the configured number of active tasks; consider cancellation, retries, backpressure, and database pool capacity in production.

~~~js
async function settleWithLimit(items, limit, task) {
  if (!Number.isSafeInteger(limit) || limit < 1) {
    throw new RangeError("limit must be a positive safe integer");
  }

  const results = new Array(items.length);
  let nextIndex = 0;

  async function worker() {
    while (true) {
      const index = nextIndex++;
      if (index >= items.length) return;

      try {
        results[index] = {
          status: "fulfilled",
          value: await task(items[index])
        };
      } catch (reason) {
        results[index] = { status: "rejected", reason };
      }
    }
  }

  const workerCount = Math.min(limit, items.length);
  await Promise.all(
    Array.from({ length: workerCount }, () => worker())
  );

  return results;
}
~~~

### 7. AbortController provides cooperative cancellation
- Create an AbortController and pass its signal to an API that supports AbortSignal.
- Calling abort() signals cancellation; fetch rejects when its request is aborted.
- A Promise itself is not forcibly cancelled: the underlying operation must observe and honor the signal.
- Aborting a client request does not guarantee that server-side work already received has been rolled back or stopped.

~~~js
const controller = new AbortController();

try {
  const response = await fetch(url, {
    signal: controller.signal
  });
  // Check response status before reading the body.
} catch (error) {
  if (error instanceof Error && error.name === "AbortError") {
    // Handle expected cancellation separately.
  } else {
    throw error;
  }
}

// Trigger from the owning cancellation path:
controller.abort();
~~~

### 8. Fetch HTTP failures are not network rejections
- fetch generally fulfills with a Response for HTTP statuses such as 404 and 500.
- Check response.ok (2xx) or response.status explicitly.
- response.json() is asynchronous and can reject if the body is not valid JSON.
- Response bodies are streams; do not assume the same body can be read repeatedly without cloning first.

~~~js
async function getJSON(url, signal) {
  const response = await fetch(url, { signal });

  if (!response.ok) {
    throw new Error("HTTP " + response.status);
  }

  return response.json();
}
~~~

### 9. Express 5 forwards rejected async route handlers
- In Express 5, a route handler or middleware returning a rejected Promise automatically forwards the rejection to next(error).
- Error-handling middleware uses four parameters: (err, req, res, next), and should be registered after routes.
- If headers have already been sent, delegate with next(err).
- Log diagnostic details server-side; do not expose stack traces or arbitrary internal error messages to clients.
- Express 4 requires explicit forwarding or an async wrapper for rejected promises.

~~~js
app.get("/users/:id", async (req, res) => {
  const user = await users.findById(req.params.id);

  if (!user) {
    return res.status(404).json({ error: "User not found" });
  }

  res.json(user);
});

app.use((err, req, res, next) => {
  logger.error({ err }, "Unhandled request error");

  if (res.headersSent) {
    return next(err);
  }

  res.status(500).json({ error: "Internal server error" });
});
~~~

### 10. Test boundary behavior with node:test
- Node's built-in node:test runner supports synchronous tests and async tests that return/await promises.
- node:assert/strict provides strict assertions without adding a third-party test dependency.
- Test boundary cases, not just the happy path: absent, present-but-undefined, inherited, malformed, out-of-range, null, array, and valid values.
- Run tests with node --test.

~~~js
import test from "node:test";
import assert from "node:assert/strict";
import { parseLimit } from "./parse-limit.js";

test("defaults only when limit is absent", () => {
  assert.equal(parseLimit({}), 20);
});

test("rejects present undefined", () => {
  assert.throws(() => parseLimit({ limit: undefined }));
});

test("does not accept inherited limit", () => {
  const query = Object.create({ limit: "5" });
  assert.equal(parseLimit(query), 20);
});

test("accepts a valid limit", () => {
  assert.equal(parseLimit({ limit: "100" }), 100);
});

test("rejects values outside the policy", () => {
  assert.throws(() => parseLimit({ limit: "101" }));
  assert.throws(() => parseLimit({ limit: "1.5" }));
});
~~~
