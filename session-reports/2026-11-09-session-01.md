## The 10 tips taught
1. Object.keys(), Object.values(), and Object.entries().
2. Object.entries() includes only own enumerable string-keyed properties; integer-index-like keys are ordered numerically first.
3. Destructuring entries in a for...of loop.
4. Filtering entries and rebuilding an object with Object.fromEntries().
5. Object.hasOwn() versus the in operator.
6. Object.assign() mutates its target and performs a shallow property copy.
7. Object spread also performs a shallow copy; nested references remain shared.
8. Object.freeze() versus Object.seal(); both are shallow.
9. map() for transformations versus forEach() for side effects.
10. sort() mutates an array; toSorted() returns a sorted copy.

## Learner answers and evaluation

### Q1 — Output prediction
- **Second console:** Correct. Learner predicted true false, showing basic understanding that in sees inherited properties while Object.hasOwn checks direct ownership.
- **First console:** Incorrect. Correct result is ["2", "10", "region"]. Object.keys() excludes inherited and non-enumerable properties; property names are strings.
- **Third console:** Incorrect. Correct result is [["2", "two"], ["10", "ten"], ["region", "IN"]]. Object.entries() has the same own/enumerable/string-keyed filtering behavior as Object.keys().
- Key gap: distinguish own properties from inherited properties, and enumerable from non-enumerable properties.
- Do not mark Object.keys()/Object.entries() as mastered.

### Q2 — Shallow-copy bug
Learner response: "i dont get the question please explain me and can mark that user dont know this concept"
- No independent solution demonstrated.
- Mark shallow copying / shared nested references as **Needs re-teaching**.
- Re-explanation delivered: object spread creates a new outer object but nested object references are shared. In the example, config.headers and defaults.headers point to the same object, so assigning config.headers.authorization mutates shared defaults and can leak request-specific state into later requests.
- Safe fix for the given two-level structure: create a new outer config and also copy headers with a nested spread, then assign the authorization field.
- Retest required before changing mastery level.

### Q3 — Query filtering and validation
- Learner attempted a guard, required-field checks, Number conversion, Object.entries(), filter(), and Object.fromEntries().
- Correctly identified that filtering allowed keys alone is insufficient to validate API input.
- Bugs and gaps:
  1. Initial condition using !query combined with a negated Object.keys(query).length comparison is logically faulty; Object.keys(null/undefined) can throw.
  2. Directly assigns converted values back onto query, mutating caller input.
  3. Truthiness checks are not robust numeric validation; use explicit integer/range rules.
  4. Does not validate sort against an allowlist of permitted values.
  5. Does not explicitly remove undefined values among otherwise allowed keys.
  6. Required-field and object-shape checks need clearer separation.
- A corrected illustrative implementation was provided using object-shape validation, allowed-key and sort-field Sets, Object.entries().filter().map(), Object.fromEntries(), Object.hasOwn(), Number.isSafeInteger(), and range checks. This is instruction, not evidence of independent mastery.
